# Veda-Core Milestone 14 Results — PCC Compartment Bounding (Sail)

**Date:** 2026-07-26
**Scope:** implements `PCC_COMPARTMENT_DESIGN.md` in full on the Sail side — bounding execution inside an `OCInvoke`-entered compartment, closing the real, narrower gap that design doc found underneath the four-milestone-old "a real PCC register with fetch-time capability enforcement" phrasing. RTL mirror deliberately not attempted this pass (see "Not yet built").

## Two real, load-bearing discoveries made while implementing the already-verified design, not assumed from the design doc alone

The design doc (Section 5a) had already verified the *conceptual* hooks (`ext_fetch_check_pc`/`ext_handle_fetch_check_error`, scattered `read_CSR`/`write_CSR`) by reading source. Actually wiring them up surfaced two more real, concrete facts only a real build could confirm:

1. **A genuine module-ordering conflict, caught by a real compile error, not predicted in the design doc.** `core/addr_checks.sail` (where `ext_fetch_check_pc`/`ext_handle_fetch_check_error` are defined by default) is part of the `core` Sail module, which `Veda` itself `requires` — meaning `core` is elaborated *before* `Veda_insts`, so a function body living in `core/addr_checks.sail` can never reference a Veda-defined register, no matter how it's written. First attempt (editing the function bodies in place in `core/addr_checks.sail`) failed with a real, unambiguous error: `Identifier veda_pcc_length is unbound`. **Fixed** by splitting declaration from definition — `core/addr_checks.sail` keeps only two forward `val` type-signature declarations (using solely core-visible types), and the real function *bodies* moved to `postlude/step_ext.sail`, which already `requires ... Veda_insts` (confirmed by reading `riscv.sail_project` — the identical real reason `ext_reset`'s own Veda-referencing body already lives in that exact file). Rebuilt clean after the move.
2. **A real, pre-existing test's own fixture needed widening, found by running the full regression, not assumed safe.** `vc_ocinvoke.S` (Milestone 10's own positive test) minted its CODE capability with `Length = 0x0040` (64 bytes) — a value that was never actually *checked* against anything before this milestone (`OCInvoke`'s own `Length` field was write-only bookkeeping until now). Once `OCInvoke` started genuinely narrowing `veda_pcc_length` to that value, `landing_pad`'s own real code plus `RVMODEL_HALT_PASS`'s own macro expansion came close enough to filling that 64-byte window that the test began to fail — a real, predictable consequence of making a previously-decorative field newly load-bearing. **Fixed** by widening the fixture's own `Length` to `0x0100` (256 bytes, generous headroom), not by weakening the new enforcement.

## Design decisions carried straight from `PCC_COMPARTMENT_DESIGN.md`, verified as implemented

- `veda_pcc_base`/`veda_pcc_length` (live compartment bounds) and `veda_mepcc_base`/`veda_mepcc_length` (saved bounds across a trap) added to `veda_regs.sail`, reset to `VEDA_PCC_UNBOUNDED` (`Length = 0xFFFF`) via `ext_reset` — confirmed this is a real correctness requirement, not styling: the default zero-initialization Sail would otherwise apply would bounds-check the very first fetch against an empty window at address 0, hard-trapping on cycle one.
- Four new CSRs (`veda_pcc_base`/`_length`/`veda_mepcc_base`/`_length` at `0x7C0`-`0x7C3`), the real, standard RISC-V "Machine-level Custom read/write" address range (`riscv-spec.pdf` Table 91, p.664), accessible via the real, unmodified base-ISA `CSRRW`/`CSRRS` — no new instruction.
- `OCInvoke`'s own success path (`veda_cap_insts.sail`) narrows `veda_pcc_base`/`_length` to the invoked code capability's own `Base`/`Length` — the real security effect real CHERI's own PCC-installation achieves, for the `Base`/`Length` subset this project found a real consumer for (`Perms`-on-PCC stays deliberately out of scope, per the design doc's own Section 7).
- `veda_trap()` (`veda_bind_insts.sail`, called by every existing Veda-Core hard-trap) now saves the live bounds into `veda_mepcc_*` and resets to unbounded before the real trap fires — real CHERI's own "Exception Code Capability" requirement (a trap handler must run in a trusted, unconstrained context).
- The new PCC-bounds-violation path itself (`postlude/step_ext.sail`'s `ext_handle_fetch_check_error`) performs the identical save-and-reset, then delivers the trap via `handle_exception` directly (not `veda_trap()`/`trap()` — a different, incompatible calling context for a fetch-time hook, confirmed from source before writing this), with `cause = 0x01` (Bounds/Length Violation, reused, no new cause code — mirrors real CHERI's own `handle_cheri_pcc_exception` reusing `CapEx_LengthViolation`) and `cap_idx = 16` (the "this was PCC, not a real capability register" sentinel, the exact same numeric value real CHERI's own `PCC_IDX = 0x10` uses for the identical purpose).
- Restoration across a trap is an **explicit software action** (reading `veda_mepcc_*` and writing `veda_pcc_*` via ordinary `csrr`/`csrw` before the handler's own `mret`), not automatic hardware — the design doc's own real finding that `xret_callback` is declared `pure` and cannot host this side effect, resolved by treating this as consistent with `mepc`'s own already-established explicit-advance-before-`mret` convention (Milestone 9), not a workaround.

## A real design choice made while writing the negative test, not pre-specified by the design doc

The design doc left open exactly *how* a trap handler should resume after a genuine compartment-bounds escape (as opposed to an ordinary, skippable "use"-family violation). `vc_pcc_bounds_neg.S` makes and demonstrates a concrete, reasoned choice: a PCC bounds violation is treated as **abandoning the compartment**, not as a single bad instruction to step over — the handler explicitly restores `veda_pcc_length` to `VEDA_PCC_UNBOUNDED` (not back to the narrow saved bounds) and redirects `mepc` to a real recovery point *outside* the compartment, never attempting to resume execution inside it. This is the same real distinction real CHERI's own PCC-bounds handling makes from an ordinary capability-register violation.

## Result

Both new Sail self-check tests passed on their first real simulation run — `vc_pcc_bounds.S` (positive: proves the unbounded→narrow→unbounded round trip via the live `veda_pcc_base`/`_length` CSRs, no traps) and `vc_pcc_bounds_neg.S` (negative: proves the real hard-trap, correct `mcause`/`mtval`/`mepc`, correct `veda_mepcc_*` save, and the full explicit-restore-and-recover cycle across a real `mret`).

## Full regression: zero net impact after the two real, understood fixes above

`run_veda_selfcheck_tests.sh` — **24/24 passed** (22 prior tests, one fixture-widened per above + `vc_pcc_bounds`/`vc_pcc_bounds_neg`), zero regressions.

## Not yet built

**RTL mirror** — deliberately not attempted this pass, matching this project's own established Sail-first sequencing (every prior milestone verified Sail before starting RTL). RTL's own version will need: `MHARTID`-style fixed persistent signals for `pcc_base`/`_length`/`mepcc_base`/`_length`; a genuinely new kind of check (unconditional, every cycle, not gated on a decoded opcode, unlike every other check in `veda_core.tlv` so far) for the fetch-time bounds test; new CSR address decode for `0x7C0`-`0x7C3` alongside the existing Milestone 9 CSR file; and `OCInvoke`'s own RTL write path extended to narrow the new persistent signals on success. `Perms`-on-PCC, S/U-mode-privilege interaction, and real multi-hart RTL all remain exactly as named in `PCC_COMPARTMENT_DESIGN.md`'s own "Deliberately out of scope" section (§7) and `MILESTONE_12_RESULTS.md`'s "Not yet built" — none touched or affected by this milestone.
