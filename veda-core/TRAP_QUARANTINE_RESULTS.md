# VEDA_TRAP_QUARANTINE: repeated-trap DoS containment (Sail + RTL)

**Date:** 2026-08-19
**Scope:** closes a real, empirically-confirmed availability gap named by an official, cross-industry-authored paper (CHERIoT RTOS, ACM SOSP '25, §5.1.2 "Repeat attacks") as explicitly NOT prevented by capabilities alone: an attacker (or a naive/compromised scheduler policy) can repeatedly trigger the same real compartment-bounds fault and immediately re-invoke, forcing the victim compartment to spend all its cycles micro-rebooting, with zero hardware pushback. Full research, design rationale, and the found-during-implementation corrections are in `TRAP_QUARANTINE_DESIGN.md`; this doc records verification for both the Sail formal model and its RTL (synthesizable hardware) mirror, plus two real security gaps an adversarial review of the RTL diff found and this session fixed on both sides.

## Empirical baseline (confirmed before any fix existed)

An earlier, unmitigated probe (retargeted into today's negative test, not kept as a separate file) drove 20 consecutive trap-then-immediate-reinvoke round trips against the identical Length=4 compartment. Traced instruction-by-instruction: zero hardware interference at any point -- no refusal, no slowdown, no signal that this compartment had just faulted the same way 19 times in a row. This is the real, confirmed gap the mechanism below closes.

## Mechanism (summary; full design in `TRAP_QUARANTINE_DESIGN.md`)

A per-compartment hardware trap counter (`veda_trap_tracker`, 8-entry linear-scan table, keyed by `otype` -- CSeal's own real per-compartment type-authority identity), incremented on every real trap taken from a live (bounded) compartment. At `VEDA_OCINVOKE`, after every existing tag/seal/otype-match/perm check already passes, a new check hard-refuses entry (`VEDA_CAUSE_COMPARTMENT_QUARANTINED = 0x09`) if that otype's count has reached the fixed threshold (3). Decay is event-based, not timer-based (this project's Sail/RTL has no CLINT wiring): any successful `VEDA_OCINVOKE`/`VEDA_OCRETURN` transition out of a live compartment is only reachable if that compartment did not fault since its last entry, so reaching it resets the departing compartment's own count to 0 -- "good behavior earns forgiveness," the identical real property `systemd`'s `StartLimitBurst` and Erlang/OTP's supervisor `MaxR` both implement in software, realized here in hardware instead. A privileged CSR (`veda_trap_quarantine_clear`, `0x7C6`) allows genuine operator recovery, gated by the same `veda_oda_authorized()` check ODT-Populate/Destroy already use.

**Real correction found during implementation** (detailed in the design doc): the record-fault call was first wired into `handle_trap_extension`, then found wrong by a failing negative test -- the actual fetch-bounds-violation trap path (`ext_handle_fetch_check_error`) calls `veda_pcc_save_and_reset()` directly, bypassing `handle_trap_extension` entirely. Fixed by moving the record-fault call into `veda_pcc_save_and_reset()` itself, the one true chokepoint all three real trap-while-bounded paths share.

**Real scope limit found during implementation**: the quarantine *check* applies to `VEDA_OCINVOKE` only, not `VEDA_OCRETURN` -- `VEDA_OCRETURN`'s `cs1.otype` is always the fixed `VEDA_OTYPE_SENTRY` sentinel (shared by every sentry in the system), not a per-destination identity; keying quarantine on it would have wrongly bucketed every distinct return target together. `VEDA_OCRETURN` still correctly decays the compartment being left.

## Verification

**Negative test** (`sail_tests/vc_repeated_trap_dos_neg.S`): a Length=4 compartment is re-invoked unconditionally on every trap, 5 times. In-program per-iteration `mtval` decoding asserts traps 1-3 are the ordinary bounds violation (`cause=0x01`, `cap_idx=16`) and traps 4-5 are the quarantine refusal (`cause=0x09`, `cap_idx=3`), confirmed individually via two independent sentinels (not inferred from a one-shot pass). `SUCCESS`, exit 0. Traced (`--trace-exception`): exact mtval sequence `0x201, 0x201, 0x201, 0x069, 0x069` -- confirms the refusal is persistent across two separate attempts, not a one-shot fluke.

**Positive test** (`sail_tests/vc_trap_quarantine_decay_pos.S`): the design doc's own stated requirement -- a compartment that faults twice, makes real forward progress via a clean `OCRETURN` (through a sentry minted before entry, mirroring `vc_ocreturn_basic.S`'s established pattern), then faults twice more, must NOT be quarantined. Both the narrow (fault-inducing) and wide (clean-body) compartments are sealed against the same never-moved type-authority capability, so they share the identical `otype=0` tracker identity by construction. Traced: exactly 4 traps total, all `mtval=0x201` (ordinary bounds violation) -- never `0x069` -- proving the streak genuinely reset between phase 1 and phase 3, not merely that phase 3 alone stayed under threshold by coincidence.

**Mutation test 1**: disabled the `VEDA_OCINVOKE` quarantine check (`else if false & veda_trap_tracker_is_quarantined(...)`), rebuilt. `vc_repeated_trap_dos_neg` correctly flipped to `FAILURE` -- the attack reverts to unmitigated (traps 4-5 no longer refused). Reverted, rebuilt.

**Mutation test 2**: disabled the `VEDA_OCRETURN` decay call (`if false & veda_pcc_length != VEDA_PCC_UNBOUNDED then ...`), rebuilt. `vc_trap_quarantine_decay_pos` correctly flipped to `FAILURE` -- phase 3's compartment is wrongly quarantined because phase 1's count never decayed. Reverted, rebuilt.

**Full regression**: `run_veda_selfcheck_tests.sh` -- **72/72 passed** (70 pre-existing + 2 new: the negative and positive tests), zero regressions. Compiler-layer suites re-run against the final rebuilt `sail_riscv_sim` binary to confirm the Sail-side change has zero effect on the toolchain's own heavy `OCInvoke`/`OCRETURN` users: `run_veda_compartment_test.sh`, `run_veda_compartment_nested_test.sh`, `run_veda_sched_demo_test.sh`, `run_veda_sched_global_combo_test.sh`, `run_veda_syscall0_hello_world_test.sh`, `run_veda_syscall0_forged_oid_test.sh` -- all `PASS`.

## RTL mirror

Ported the full mechanism into `veda-core/rtl/veda_core.tlv` via a multi-agent workflow (parallel audit of the RTL's existing `OCInvoke`/`OCReturn`/trap-reset/CSR-gate/table conventions, a single implementation pass against that map plus this design's own Sail-verified spec, then independent adversarial correctness/security review and a fresh mutation-test confirmation, none of which trusted the implementer's own self-report). New `$veda_pcc_otype` register (mirrors `$veda_pcc_base`/`$veda_pcc_length`'s exact priority-mux shape), a hand-unrolled 8-entry `$veda_tt0..7_{valid,otype,count}` table (no generate-loop/linear-scan precedent existed anywhere in this file before), `$veda_ocinvoke_quarantined` OR'd in as the last arm of `$veda_ocinvoke_violation` (cause `5'h09`, confirmed genuinely free in RTL's own cause-code space), decay wired into both `OCInvoke` and `OCReturn`'s success arms at the exact same `$veda_trap_taken` chokepoint the table's own record-fault logic uses, and CSR `0x7C6` gated by the identical `($priv || $veda_oda_authorized)` expression already used for ODT-Populate/Destroy. Two new smoke tests (`veda_smoke_trap_quarantine_neg.S`/`veda_smoke_trap_quarantine_decay_pos.S`) mirror the Sail negative/positive tests exactly, GPR-readback convention, fresh Object_IDs. Full RTL smoke regression **65/65 passed**, ACT4 RV64I conformance **51/51 passed**, both mutation tests (drop the OCInvoke quarantine check; drop the OCReturn decay term) independently re-confirmed live by the review's own third agent, not reused from the implementer's run.

## Adversarial review findings and fixes (found after the RTL mirror, before this milestone was considered closed)

The RTL mirror's own adversarial security review (a dedicated agent instructed to try to refute the implementation, not just confirm it) surfaced two real, concrete gaps -- both independently re-verified by direct reading of the actual Sail source before any fix was written, per this project's own "refute findings before recording them" discipline, and both closed on the side(s) that needed it:

**1. `write_CSR(0x7C6, ...)` authorization gap (Sail only -- RTL was already correct).** Sail's actual gate checked `cur_privilege == Machine` only, contradicting its own source comment (and this design doc's original text) which said it should also accept `veda_oda_authorized()`, matching every other ODA-gated write in the project (`VEDA_ODT_POPULATE`/`DESTROY`). Confirmed by direct read of `veda_regs.sail`: the comment claimed the OR-gate, the code didn't have it. RTL's own independent implementation had already been built correctly against the documented intent (`$veda_tt_clear_active` gates on `$priv || $veda_oda_authorized`), so this was a Sail-side omission, not a real RTL-vs-Sail behavioral question -- fixed by adding the missing `| veda_oda_authorized()` to Sail's `write_CSR(0x7C6, ...)`, with a forward `val` declaration in `veda_regs.sail` (the identical cross-file pattern `exceptions/sys_exceptions.sail` already uses, since `veda_regs.sail` compiles before `veda_ocl_insts.sail` where `veda_oda_authorized()` is really defined). New test `sail_tests/vc_trap_quarantine_csr_clear_pos.S` closes a separate, real coverage gap the review also surfaced -- no Sail test exercised CSR `0x7C6` at all before this pass -- proving the CSR genuinely clears a tracker entry (quarantine, clear, re-fault ordinarily) rather than just reviewing that the gate expression looks right.

**2. Trap-tracker eviction starvation bypass (Sail + RTL, present identically on both -- a real design gap, not introduced by the RTL port).** The original eviction policy (plain global-minimum-count victim) let an attacker who controls several OTHER otypes drive them all to the quarantine threshold (count==3, itself already "quarantined") and force the table's next fresh fault to evict a genuinely quarantined VICTIM entry, silently un-quarantining it -- reopening the exact DoS this milestone exists to close. Re-derived and confirmed directly from `veda_trap_tracker_record_fault`'s own source before accepting the finding. Fixed on both sides with the same real invariant: a non-quarantined (`count < threshold`) entry always has a strictly lower count than any quarantined (`count >= threshold`) one, so a quarantined entry is never evicted in preference to a non-quarantined one -- **Sail**: an explicit "prefer a safe victim, else do nothing" three-pass rewrite of the eviction search. **RTL**: a much smaller, mathematically-equivalent diff -- the existing global-minimum-count search already always lands on a safe entry whenever one exists (since safe counts are strictly lower), so only one new signal was needed, `$veda_tt_any_safe = ($veda_tt_min_count < 4'd3)`, gating the final eviction write. New test `sail_tests/vc_trap_quarantine_starvation_pos.S` drives all 8 table slots to simultaneous quarantine (otypes 0-7, one shared re-populated CODE object + a single type-authority capability with 8 OCA-derived `Offset` values, keeping every individual faulting PC's own repeat count at 3 to stay clear of the simulator's own unrelated trap-loop-detection heuristic), confirms a fresh 9th otype's fault does not evict anyone, then confirms the otype-0 victim is still refused. Traced: 25 ordinary-bounds traps (`mtval=0x201`) followed by exactly one quarantine-refusal trap (`mtval=0x069`) as the very last event. Mutation-tested on both sides (Sail: reinstate the old fallback branch; RTL: force `$veda_tt_any_safe` to `1'b1`) -- both correctly flip the respective test to `FAILURE`/fail; both reverted cleanly, full regression restored.

One residual, explicitly-named edge case remains on both sides, not claimed closed: if literally all 8 tracked entries are simultaneously quarantined (requires driving 7 OTHER distinct compartments to full quarantine, not just occupying free slots -- a strictly harder, much noisier attack, and itself a loud operational signal), a fresh fault against a never-before-seen 9th otype is left untracked for that one instance rather than evicting anyone; no EXISTING quarantine is ever weakened by this case.

**Full regression after both fixes**: Sail self-check **74/74 passed** (72 prior + 2 new: the CSR-clear and starvation tests), compiler-layer suites spot-checked clean (`run_veda_compartment_test.sh`, `run_veda_sched_demo_test.sh`, `run_veda_syscall0_forged_oid_test.sh`).

**RTL-side ports of the same two new tests** (`veda_smoke_trap_quarantine_starvation_pos.S`/`.sv`, `veda_smoke_trap_quarantine_csr_clear_pos.S`/`.sv`, Object_IDs 550-552/560-562, grep-audited fresh): confirmed OCA's RTL encoding (`funct7=0x0a`, `funct3=0x1`, `opcode=0x5b`) and the `veda.odt.populate` 64-bit descriptor packing are bit-for-bit identical to Sail's own, so the port needed no encoding translation. Both new tests passed on the first build; the starvation test's own total real-trap count came back exactly `26` (24 phase-1 + 1 phase-2 + 1 phase-3), matching the Sail side's prediction exactly. **RTL full regression: 67/67 smoke passed (65 prior + 2 new), 51/51 ACT4 passed, 0 failed, 0 timed out** -- independently re-confirmed by a second, fresh run of both suites (not reused from the porting pass's own log). Both RTL-side mutation tests independently re-run and confirmed: forcing `$veda_tt_any_safe` to `1'b1` flips the starvation test to `FAILURE` (fail sentinel `0xBAD9`, the victim's entry evicted and showing the ordinary cause instead of quarantine refusal); forcing `$veda_tt_clear_active` to `1'b0` flips the CSR-clear test to failure (the compartment stays quarantined forever, the CSR write becomes a genuine no-op). Both reverted cleanly (`git diff` confirmed byte-identical to the pre-mutation single-line definitions each time), full 67/67 + 51/51 regression restored after each revert.

## Not yet built

**Configurable threshold/table size** -- fixed constants (`threshold=3`, `8` entries) for this milestone, matching the design doc's own stated deferral; a CSR-configurable form is a natural future step once a real consumer exists, mirroring how `veda_attr` was only added after `VEDA_ODT_POPULATE`'s simpler fixed-descriptor form shipped first.

**Multi-hart interaction** -- out of scope by the same construction every other Veda-Core mechanism in this line already is; this project's compartment/trap model is confirmed single-hart throughout.

**A real per-destination-address quarantine key for `OCRETURN`** -- named as a plausible future extension in the design doc, not built here.

**The all-8-simultaneously-quarantined residual edge case** -- named explicitly above, not silently dropped; closing it fully would need either a recency/age field per tracker entry (a real design change, not a small fix) or accepting the current bounded, self-limiting behavior.

**Not committed or pushed yet**, matching this session's established pattern.
