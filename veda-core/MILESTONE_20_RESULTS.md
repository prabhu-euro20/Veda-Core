# Veda-Core Milestone 20 Results — Compartment-State CSR Self-Escape Fix (Sail)

**Date:** 2026-08-01
**Scope:** closes a real, empirically-confirmed vulnerability found while continuing the same security-audit rigor that produced Milestone 19, directly targeting the compartmentalization/purecap machinery Milestones 14 and 19 just built: code entered via a real `OCInvoke` compartment could simply execute an ordinary `CSRRW` to its own compartment-state CSRs to undo its own bounding, with zero trap or restriction.

## The vulnerability, empirically confirmed before any fix was designed

`veda_pcc_base`/`veda_pcc_length` (`0x7C0`/`0x7C1`, Milestone 14's live compartment bounds), `veda_mepcc_base`/`veda_mepcc_length` (`0x7C2`/`0x7C3`, the trap-time save registers), and `veda_mode` (`0x7C5`, Milestone 19's purecap toggle) are all accessed via the **standard, generic RISC-V Zicsr `CSRRW`/`CSRRS`** — an ordinary base-ISA instruction, not a Veda-specific one. Direct read of `extensions/Veda/veda_regs.sail` confirmed `is_CSR_accessible` for all five checked only `currentlyEnabled(Ext_Veda)` — nothing about whether the currently-executing code is inside a live, narrowed compartment. Real-world grounding, not invented: a WebSearch of real CHERI's own documentation confirms its actual rule — *"Reading or writing any CSR requires the Access_System_Registers permission on the PCC."* Veda-Core had no equivalent gate at all.

Before writing any fix, this was reproduced live with a real, throwaway PoC under `sail_riscv_sim`: a real `OCInvoke` narrows `veda_pcc_length` to `0x0040`; from inside the compartment, `li t3,0xFFFF; csrw 0x7c1,t3` executes with zero trap; execution then continues past the compartment's original boundary with zero trap (`SUCCESS` at the "escape worked" sentinel). This required no special preconditions — it works with only M-mode enabled, no S/U-mode needed, using only instructions and CSRs that already existed.

## Design validated by an independent Plan agent before implementation

A Plan agent, given the confirmed vulnerability and a first-draft fix design, was asked to verify every claim by reading source directly rather than trusting the summary, and made one material correction plus two honest scoping decisions:

- **Correction**: the original draft assumed `write_CSR` had no channel to signal a trap (matching `0x7C5`'s own pre-existing comment, which was itself wrong and is now fixed). Direct read of `core/csr_begin.sail`'s real declared signature (`val write_CSR : (csreg, xlenbits) -> result(xlenbits, unit)`) and `extensions/Zicsr/zicsr_insts.sail`'s real dispatch (`Err(()) => Illegal_Instruction()`) confirmed a real, already-proven, idiomatic hard-trap mechanism exists and should be used — a stronger, more consistent response than a silent no-op, matching every other Veda security violation's own hard-trap behavior.
- **A second real attack identified, not just the one in the original PoC**: the same unconditional-write gap generalizes to `veda_mepcc_base`/`_length` (`0x7C2`/`0x7C3`) — code inside a compartment could corrupt the *saved* trap-time bounds a legitimate handler's own restore convention would later trust, not just the *live* bounds. Gated identically.
- **`veda_attr` (`0x7C4`) confirmed correctly out of scope**: its sole consumer, `VEDA_ODT_POPULATE_FAST`, already has its own independent capability-authority gate (`veda_oda_authorized()` OR M-mode, Milestone 11) — a compartment rewriting `veda_attr` alone cannot use it for anything without separately satisfying that unrelated check.
- **A second, distinct, real gap found and deliberately deferred**: `mtvec` (the standard, non-Veda trap-vector CSR) is completely ungated by compartment-awareness, and — confirmed by reading `postlude/step.sail`'s real `try_step` dispatch and grepping for `veda_pcc_save_and_reset`'s only 3 real call sites (`veda_trap()`, `ext_handle_fetch_check_error`, `ext_handle_data_check_error`) — an *ordinary* RISC-V exception (`ecall`, illegal instruction, misaligned access) does **not** reset `veda_pcc_base`/`_length` at all. A compartment could rewrite `mtvec`, then deliberately trigger an ordinary exception, landing in an attacker-controlled handler still running with the compartment's own narrowed bounds live (and `veda_mepcc_*` left stale/unsaved from whenever the last real Veda trap left them, silently misleading any code that trusts them after *any* trap). This does not, by itself, escape the compartment's own fetch bounds (a handler placed outside them would immediately fetch-fault) — but it is a real, independent trap-state-integrity gap distinct from this milestone's own fix, named honestly and deliberately scoped out (see "Not yet built").

## Fix implemented

`extensions/Veda/veda_regs.sail`: `write_CSR` for `0x7C0`, `0x7C1`, `0x7C2`, `0x7C3`, and `0x7C5` now requires `veda_pcc_length == VEDA_PCC_UNBOUNDED` (not currently inside a live compartment). If violated: call `veda_pcc_save_and_reset()` (the identical discipline every other real Veda trap already follows, so the resulting handler runs unconstrained, not still narrowed) and return `Err(())` — a real `Illegal_Instruction` hard-trap (`mcause=2`), not a silent no-op. `0x7C5` combines this with its existing, unmodified M-mode check.

Read access is deliberately **not** gated on any of the five — matches this codebase's own already-established "capability metadata is always inspectable" principle (`veda_cap_insts.sail`'s query-family comment, the same reasoning behind `CGetTag`/`CGetType` working on sealed/untagged capabilities): code inside a compartment already knows its own bounds (it got there via the capability that defined them), so reading them back leaks nothing new.

`OCInvoke`'s own legitimate narrowing/widening (`veda_cap_insts.sail`, `veda_pcc_base = cs1.Base; veda_pcc_length = cs1.Length;`) is a direct Sail register assignment, confirmed via source read to never go through `write_CSR` at all — completely unaffected by this fix, by construction.

## Test plan and result

Three new `sail_tests/vc_*.S` tests, following the established self-checking convention:

- **`vc_pcc_csr_escape_neg.S`** — the permanent regression test for the empirically-confirmed PoC: inside a real `OCInvoke` compartment (`Length=0x0040`), attempts `csrw 0x7c1, 0x1000` (a value distinct from both the original `Length` and `VEDA_PCC_UNBOUNDED`, so success vs. failure is unambiguous from the final CSR value alone) — now hard-traps (`mcause=2`), and the handler's load-bearing assertion confirms `veda_pcc_length` reads exactly `0xFFFF` afterward (proving neither the original nor the attacker's value persisted, and the handler itself runs unconstrained).
- **`vc_pcc_csr_escape_mepcc_neg.S`** — the second attack the fix also closes: attempts `csrw 0x7c3, 0x2000` from inside the same compartment fixture — hard-traps, and the handler confirms `veda_mepcc_length` reads exactly `0x0040` (the real, legitimately-saved value), not the attacker's `0x2000`.
- **`vc_pcc_csr_mepcc_outside_positive.S`** — a real, previously-uncovered case (every existing test only ever *read* `0x7C2`/`0x7C3`, inside a trap handler, never wrote them from ordinary code): confirms write/readback of `veda_mepcc_base`/`_length` from outside any compartment still works exactly as before. `0x7C0`/`0x7C1` deliberately not exercised with arbitrary values in a dedicated new positive test — doing so risks immediately tripping Milestone 14's own real PCC-fetch enforcement on the test's own next instruction fetch (`veda_pcc_base`/`length` jointly define the live fetch window); the existing, unmodified `vc_pcc_bounds.S`/`vc_pcc_bounds_neg.S` already exercise that case safely (via `OCInvoke`'s own legitimate path and the trap-handler-restore path respectively) and remain in the regression corpus.

`run_veda_selfcheck_tests.sh` — **40/40 passed** (37 pre-existing + 3 new), zero regressions on the first run — including `vc_pcc_bounds_neg.S`'s own trap handler, whose real `csrw 0x7c1,0xFFFF; csrw 0x7c0,x0` restore sequence continues to succeed unchanged, confirmed empirically rather than just argued: by the time any Veda trap handler runs, `veda_pcc_save_and_reset()` has already reset `veda_pcc_length` to `VEDA_PCC_UNBOUNDED`, so this milestone's new gate condition is already satisfied before the handler's own restore writes ever execute.

## Not yet built

**RTL mirror** — deliberately not attempted this pass, matching this project's own established Sail-first sequencing. Confirmed via direct grep of `veda_core.tlv` that RTL has not mirrored Milestone 19 either yet, so this exact same CSR-write escape exists unfixed in RTL too — a named, combined RTL follow-up (Milestones 19+20 together) rather than two separate small RTL passes.

**The `mtvec`-rewrite / ordinary-exception trap-state-integrity gap** (found during this milestone's own design review, not fixed here) — a compartment can rewrite the standard `mtvec` CSR and deliberately trigger an ordinary, non-Veda exception to reach a handler that still observes stale `veda_pcc_*`/`veda_mepcc_*` state, since only Veda-recognized traps (`veda_trap()`, the Milestone 14/19 hooks) currently call `veda_pcc_save_and_reset()` — the generic `handle_exception`/`exception_handler` path used by `ecall`/illegal-instruction/misaligned-access does not. Scoped as a real, separate, honestly-named future milestone (21) rather than bundled into this one, matching this project's own "one milestone, one real change" discipline.

**Update, 2026-08-10**: the "not independently exploitable" reasoning above (fetch-check backstop on a handler outside the compartment's own bounds) held only while PCC stayed narrowed across an ordinary trap. Milestone 21's own fix (universal PCC-reset-on-any-trap, shipped later the same day as this milestone) removed exactly that condition, which nobody re-examined against this specific gap at the time. The two composed into a real, empirically-confirmed privilege-escalation vulnerability — CLOSED, see `MILESTONE_27_MTVEC_CSR_GATE_RESULTS.md`: `mtvec` writes are now gated identically to `veda_pcc_*`/`veda_mode` (require `veda_pcc_length == VEDA_PCC_UNBOUNDED`, hard-trap otherwise), mirroring this codebase's own real Smstateen `check_CSR`-hook precedent.
